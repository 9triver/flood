# 06 · 内核重设计：操作系统语义

> 分支 `feat/domain-os-kernel-redesign`。本文档定义第二代内核（包 `dos/`）。
> 它**不沿用**第一代（`domain_os/`，见 00–05 篇）的 Resource / Observation /
> Projection / Intent → Policy → Command → acknowledged → Reconcile → confirmed
> 抽象——那套本质上是"审批工作流"。第二代回到操作系统本身解决了什么这个问题。

## 1. 判断标准

一个 OS 的味道不来自概念名词，而来自三条铁律：

1. **内核不信任用户态**：智能体对世界的一切访问都经过统一 syscall 入口，逐条做能力检查与审计；
2. **世界状态只有一份可信副本**：在内核里，用户态只能拿到带代次的快照；
3. **发出命令不等于改变现实**：命令开启事务，由后续遥测证据经一致性检查器裁决。

Agent Runtime 之上缺的正是这五样东西（等价于没有 OS 的裸机编程）：统一设备访问层、唯一可信状态、syscall 边界、进程管理、一致性保障。**dos 的使命：把领域世界变成一台虚拟机，让任何智能体像调 syscall 一样安全地感知和操作它。**

## 2. 内核结构（每个模块是一个 OS 器官）

| 模块 | OS 角色 | 职责 |
|---|---|---|
| `dos/journal.py` | WAL | 只追加的不可变事实日志；一切生效前先记账 |
| `dos/namespace.py` | 文件系统 + 页缓存 + inotify | 世界挂载为层次路径空间；commit 推进 generation；`watch` 订阅；`derive` 注册可失效重建的派生视图（缓存失效有统一定义：依赖上游 generation 前进即作废） |
| `dos/devices.py` | 驱动 + 中断 | 驱动三角色：top-half 收中断（原始不可信）、bottom-half `normalize` 归一化提交、downlink `dispatch`；`privileged_actions` 声明需特权提升的动作；`verify` 是 fsck 规则 |
| `dos/capabilities.py` | 能力令牌 | 不可伪造的随机令牌是权威的唯一通货；grant 到子树 + 动作集合 |
| `dos/consistency.py` | fsck + 看门狗 | 未决事务：遥测证实 → committed；证伪 → failed；超时 → **unknown 并冻结该路径**（重开闸门不是幂等的，绝不盲目重发）；`thaw` 显式解冻 |
| `dos/process.py` | systemd unit + 调度器 | 智能业务过程 = 受监督用户进程：声明 watches/能力/优先级/重启策略；调度器按事件唤醒、按优先级执行；进程间只经命名空间与 syscall 通信，无共享内存 |
| `dos/kernel.py` | 内核装配 | mount / grant / spawn；syscall 面 `read` `watch` `derive` `act` `approve`；`pump()` 一个确定性内核节拍：泄中断 → journal → namespace commit → fsck → 调度一个周期 |

## 3. `act()` —— 唯一的变更 syscall

```
act(token, path, action, args, expect)
  1. 冻结检查       路径若有 unknown 未决事务 → FrozenPathError
  2. 能力检查       令牌须覆盖 path+action，否则 CapabilityError（且不记账）
  3. 前置校验       expect（路径→期望值）不成立 → PreconditionError（CAS 语义）
  4. 记账           journal 先写 intent，再有任何副作用
  5. 特权门         privileged 动作挂起为 awaiting_approval，approve()（pkexec）后继续，审批本身入 journal
  6. 派发           driver.dispatch 下发；开未决事务与期限；现实是否改变由遥测经 fsck 裁决
```

事务状态机：`open → (awaiting_approval) → dispatched → committed | failed | unknown`。

## 4. 闭环全景

```
设备(遥测站/业务系统/模型服务)
  │ 中断（原始、不可信）
  ▼
驱动 normalize → Journal 追加（不可变事实）→ Namespace commit（generation 前进）
  ▼
watch 唤醒 → 调度器按优先级运行进程（智能体在用户态 handler 内被调用）
  ▼
read/derive 命名空间 → 确定性模型判断
  ▼
act() → 能力→前置→记账→(审批)→派发
  ▼
新中断 → fsck 裁决未决事务 → committed / failed / unknown(冻结)
```

进程骨架由内核确定性管理：模型挂了按重启策略兜底，超限进 `failed`——"大模型组织专业能力，而不是替代专业能力"。

## 6. 与第一代的对应与刻意差异

第一代的正确工程直觉在此不是孤立概念，而是 OS 机制的自然推论：

- Projection 可重建 → 派生视图 = 页缓存（可随时丢弃重建，失效规则统一）
- Command 需确认、outcome_unknown 不重发 → 未决事务 + fsck + 路径冻结
- 审批流 → 特权提升（approve 本身入 journal，可审计）
- 策略约束 → 能力令牌（授予即范围，检查在 syscall 边界）

刻意不做的：不做完整插件框架，扩展点仍是五个——设备驱动、能力授予、派生
视图、进程单元、fsck 规则。
