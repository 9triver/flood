> 文档状态：持续更新
>
> 更新日期：2026-08-27
>
> 当前里程碑：洪水自动演进、预测、影响评估、查询控制与 GIS/OAG 只读消费链已进入 Domain OS

## 1. 为什么重新定义这个系统

项目最初是一个以珊瑚河洪水演进为背景的水路联动应急智能体应用。它已经具备 GIS 态势展示、洪水预测、影响分析、路线规划、事件智能体和应急指令等完整演示能力，但这些能力主要围绕一个具体应用组织。

在继续抽象 Agent OS 和插件内核的过程中，我们发现真正需要解决的问题并不是“如何再造一个 Agent Runtime”，而是：

> 当 Agent 要长期参与真实行业运行时，谁负责持续连接现实世界、维护可信领域状态，并把不确定的模型意图转化为安全、可审计、可确认的现实操作？

Pi、OAG 以及其他 Agent Runtime 已经能够承担模型交互、工具编排和任务循环。行业系统仍然缺少的是它们与 IoT 设备、业务系统、专业模型和行业规则之间的统一运行边界。因此，项目定位调整为 **面向智能体的领域操作系统**。

这里的操作系统不是 Linux 的仿制品，也不是聊天机器人的包装层。它是一套长期在线的领域运行环境：向下管理领域基础设施，向上为不同 Agent Runtime 提供稳定、受治理的领域接口。

## 2. 核心设计判断

### 2.1 现实世界是系统中心，Agent 不是

内核的生命周期不跟随一次对话或一次任务。即使没有 Agent 正在运行，水文站仍在上报、设备仍可能断线、命令仍可能等待确认、领域状态仍需要持续更新。

因此，内核围绕 `Resource`、`Observation`、`Projection`、`DerivedProduct`、`Capability`、`Intent` 和 `Command` 建模。模型、Prompt、会话和 Agent Memory 留在外部 Agent Runtime 中。

这一边界带来两个结果：

1. Pi、OAG 或未来的其他 Agent 可以替换，而领域状态和控制记录不会随之迁移。
2. 没有大模型参与时，系统仍然可以执行数据接入、规则判断、审批和状态协调。

### 2.2 Agent 提交 Intent，不直接操纵协议

Agent 应表达“将水文站采样间隔调整为 10 秒”，而不是生成 MQTT topic、设备寄存器或厂商 JSON。

```text
Agent Intent
  → Resource / Capability 校验
  → Policy 决策
  → Command
  → Driver
  → MQTT、HTTP、OPC UA 或设备 SDK
```

这样可以把领域目标与协议实现分开，也可以确保认证信息、topic ACL 和设备命令格式不会暴露给大模型。

### 2.3 Observation 是事实，Projection 是可重建视图

基础设施消息首先成为不可变 `Observation`。它同时保存观测时间、系统接收时间、数据质量、来源和可选序号。

当前权威状态 `Projection` 从 Observation 派生：

- 重复 Observation 不重复处理；
- 迟到数据保留但不倒退当前状态；
- `bad` 数据保留但不进入权威状态；
- 重启后使用同一规则重新构建 Projection。

Projection 不作为另一份真相独立持久化。这个取舍使系统始终能够解释“当前状态来自哪条事实”。

### 2.4 派生产物不能冒充现实事实

洪水预测推动内核增加了 `DerivedProduct`。它用于表达有输入血缘、生产者、生成时间和有效时间的计算产物，包括未来边界条件快照、CNN 预测、后续影响评估或路线方案。

它不是另一种 Projection：产品可以在某个未来区间有效，但只有真实遥测才能更新当前权威状态。这个边界使 Agent 能同时看到“现在发生了什么”和“模型认为未来可能怎样”，而不会混淆两者。

### 2.5 接受命令不等于改变现实

普通工具调用经常把函数返回成功当作任务成功。真实基础设施中，这个假设不成立：MQTT 发布成功只表示 Broker 接收消息，设备可能尚未收到、拒绝执行或执行后未达到目标状态。

因此命令明确区分：

```text
dispatching → acknowledged → confirmed
      │               │
      ├── failed      └── 等待后续 Observation
      │
      └── 进程中断后 outcome_unknown
```

`confirmed` 必须由命令下发之后的新 Observation 与期望状态匹配产生。下发前恰好相同的旧状态不能确认新命令。

### 2.6 不确定结果必须显式化

如果进程在 `dispatching` 阶段中断，系统无法仅凭本地数据确定基础设施是否已收到命令。自动重发可能导致闸门重复动作等现实风险，因此恢复时将命令标记为 `outcome_unknown`，等待查询、遥测或人工处置。

这体现了内核的安全原则：不知道结果时保留不确定性，不用一个方便但虚假的成功或失败状态掩盖它。

### 2.7 协议位于边缘，领域语义位于中心

MQTT 只是第一个基础设施协议。内核不认识 topic，也不依赖 Eclipse Paho。职责分为两层：

- Transport 处理连接、TLS、SUBACK、QoS、重连和重订阅。
- Driver 将协议消息映射为领域 Observation，将 Command 映射为协议命令。

未来接入 HTTP、OPC UA、数据库 CDC 或厂商 SDK 时，不需要修改领域运行模型。

### 2.8 持久化事实与控制记录，不持久化运行对象

`DomainStore` 保存 Observation、DerivedProduct、Command 和 Domain Event。Resource、Capability、Driver、连接对象和 Agent 会话不进入数据库，它们由当前领域配置重新装配。

这避免了两个问题：

1. 将连接句柄或实现类误当成可恢复业务状态。
2. 领域配置升级后，数据库反向决定当前系统应该加载哪些代码。

### 2.9 先做纵向闭环，再抽象插件系统

DeepSeek Harness 的 Everything is a Plugin 思想说明了接口隔离和可替换组件的价值，但当前阶段不复制完整插件框架、依赖解析器或动态模块系统。

内核先保留几个明确扩展点：

- `InfrastructureDriver`
- `DomainPolicy`
- `DomainStore`
- `MqttTransport`
- Domain Event subscriber

只有当水文监测、洪水预测、水工程控制等多个真实模块出现相同装配需求时，才继续提炼插件发现、生命周期和依赖关系。这样可以避免先设计一个完善但没有领域证据支撑的平台。

## 3. 分层结构

当前系统分为五个职责层：

```text
Agent Runtime / 人 / 业务应用
              │ Event、Query、Intent、Approval
              ▼
┌──────────────────────────────────────────────┐
│ Domain Runtime                              │
│ Resource / Projection / Product / Event     │
│ Intent / Policy / Command / Reconciliation  │
└──────────────────────────────────────────────┘
              │                      │
              ▼                      ▼
       Domain Package             DomainStore
  水利类型、能力、规则、Driver      SQLite reference
              │
              ▼
    Infrastructure Driver
              │
              ▼
 Transport / Protocol / Infrastructure
 MQTT、HTTP、设备、业务系统、专业模型
```

| 层次 | 当前职责 | 不应包含 |
|---|---|---|
| Agent Runtime | 推理、会话、任务规划、提出 Intent | 设备协议和最终权限判断 |
| Domain Runtime | 状态、产品、事件、策略、命令和协调 | 水利专有字段和 MQTT topic |
| Domain Package | 水利语义、资源装配、能力约束和 Driver | Agent 框架内部对象 |
| Driver / Transport | 协议转换、连接可靠性和设备交互 | 自然语言推理 |
| DomainStore | 事实、产品、命令和事件的持久化 | 连接对象、Prompt 和 Agent Memory |

### 5.3 已实现的水利参考闭环

当前参考对象是珊瑚河水文站 `808J1510`：

```text
Resource:   water.station/808J1510
Capability: water.station.set-sampling-interval
Driver:     water.infrastructure.mqtt-hydrology
```

闭环已经覆盖：

1. MQTT telemetry 转换为 `sampling_interval_seconds` 和水位 Observation。
2. Observation 更新水文站 Projection。
3. Agent 提交调整采样间隔的 Intent。
4. `controlled` 风险策略要求操作员审批。
5. Driver 发布 QoS 1 MQTT Command。
6. Command 进入 `acknowledged`。
7. 后续 telemetry 报告目标采样间隔。
8. Reconciliation 将 Command 更新为 `confirmed`。

### 5.4 已实现的洪水预测闭环

`domains/flood/forecast_domain.py` 已实现第二条水利纵向路径：

1. 演进 Driver 每步只上报当前四边界流量、降雨、水库状态和 sequence Observation。
2. 当前 Observation 更新各 Resource 的 Projection。
3. 场景提供的当前至未来 24 小时窗口形成不可变预测输入 DerivedProduct，不提前写成 Observation。
4. 确定性规则判断窗口总流量峰值是否超过 `230 m3/s`。
5. 规则 Actor 提交运行 CNN 的 Intent，Policy 生成低风险 Command。
6. 计算型 Driver 执行真实 CNN，并返回带输入引用和有效时间的预测 DerivedProduct。
7. 成功发布 `water.flood.forecast.generated`；失败保留 failed Command 并发布显式失败事件。

预测结果不会更新流域 Projection。测试已覆盖成功、未触发、模型失败和 SQLite 跨重启恢复；真实检查脚本直接使用仓库 CSV 与 Git LFS 权重。

### 5.5 已实现的影响评估闭环

`domains/flood/impact_domain.py` 已实现第三级水利产品路径：

1. 组合装配订阅具体预测产品生成事件，确定性提交默认影响分析 Intent。
2. Driver 显式读取输入产品的最大水深或时间序列文件，不访问 `latest` 指针。
3. 预测水深恢复为水动力网格，与设施、桥梁、转移对象、道路和路线执行确定性空间叠加。
4. 分析参数形成稳定签名，相同输入与参数幂等复用，参数变化生成不同产品。
5. 输出产品记录预测引用、对象库版本、分类汇总、对象明细和 JSON 报告。
6. 空分析结果仍为 confirmed 产品；模型或对象库错误进入 failed Command。

旧 `analyze_inundation_impacts()` 接口保持兼容，并委托给同一个显式网格分析核心。真实检查识别出 13 个当前参数下的受影响对象，证明预测产品可以作为第二级计算的稳定输入。

### 5.6 查询、事件、GIS 与 OAG 消费边界

当前读取面不依赖具体 Agent Runtime：

- Query Service 查询 Resource、Projection、DerivedProduct、Command 和 Domain Event；
- HTTP API 提供分页/游标读取，Domain Event SSE 只传递持久化领域事件；
- GIS 适配器从明确的预测或影响产品 ID 读取 artifact，并返回兼容旧前端的 DTO；
- OAG 保持在 Domain OS 外部，只获得只读查询工具和经过校验的事件上下文；
- 后台事件处理只传递事件中真实关联的产品 ID，不用其他运行的 `latest` 补齐缺失关系。

因此 GET 请求不会触发 CNN、影响分析或其他领域计算，前端刷新和 Agent 查询也不会改变领域状态。`latest` 只允许用于用户明确要求的浏览入口，不能作为计算链或事件链的隐式依赖。

### 5.7 Intent、审批与 Command 接入边界

控制 API 已覆盖 Intent 提交、Command 查询、批准和拒绝，并统一进入既有 Policy 与 Command 状态机。HTTP 请求不直接调用 Driver；`DomainRuntimeHost` 在专用事件循环线程中持有 Domain Runtime、SQLite Store 和异步对象，请求线程通过宿主提交协程并等待结构化结果。

这一实现解决了运行时生命周期和跨线程访问问题，但当前调用方身份仍来自请求字段。认证、Capability 级授权、租户隔离和 OAG 写工具在生产使用前仍必须补齐。

### 5.8 Domain OS 自动演进生产者

配置 `--domain-database` 后，原应用的自动演进由 `DomainPlaybackController` 驱动，并在 `DomainRuntimeHost` 的事件循环上执行 `FloodImpactDomainSystem.advance()`：

- 支持 start、pause、resume、stop、reset、step、speed 和自动暂停；
- 新旧播放路径共用无副作用的 `build_boundary_flow_observation()`，避免边界数据计算分叉；
- `/api/autonomy/stream` 只承担 UI 运行状态和边界流量进度，不再执行阈值判断、预测调度或 OAG 调用；
- 持久化 Domain Event 继续由 `/api/domain/events/stream` 发布；
- 未配置领域数据库时保留旧 `EventRuntime`，作为兼容回退路径；
- 上传的边界来源通过共享注册表同时服务旧播放路径和 Domain 播放路径。

这完成了既有自动演进生产侧向 Domain OS 的切换，同时没有删除旧应用的无数据库运行方式。

### 5.9 场景运行与 `projection_epoch`

场景 reset 或重新 start 可能从比历史 Observation 更早的模拟时间开始。单纯按观测时间拒绝倒退会让新运行无法更新 Projection，因此每次新场景运行分配递增的 `projection_epoch`：

- 同一 epoch 内继续执行 Observation 幂等、质量和观测时间规则；
- 更高 epoch 可以从较早模拟时间建立新的 Projection；
- 旧 epoch Observation 作为不可变事实继续保留，但不能重新取得当前 Projection 所有权；
- SQLite 恢复按 Observation 持久化顺序重放，重启后仍恢复到最高有效 epoch 的当前视图。

该语义保留完整历史，又使演示场景和未来的重算任务可以明确开启一次新的权威视图运行。

### 5.10 持久化与恢复验证

SQLite Store 已验证以下恢复行为：

- Observation、DerivedProduct 和 Domain Event 跨进程保留；
- Projection 不落库，通过 Observation 重建；
- `acknowledged` Command 重启后继续等待反馈；
- 重启后新的匹配遥测仍可完成 `confirmed`；
- 遗留 `dispatching` Command 转为 `outcome_unknown`；
- 不会因为重启自动重复发布控制命令。
- 新场景 epoch 跨重启恢复后仍保持 Projection 所有权。

## 7. 本轮结论与后续问题

### 7.1 演进事实与未来输入已经分离

现有边界流量演进现在通过 Driver 报告当前 Observation，规则通过 Projection 更新事件启动。未来 24 小时 CSV 数据被视为场景预测输入，并作为 DerivedProduct 固化，而不是提前写入事实日志。

当前实现回答了核心语义问题，但生产化仍需补充断点续播、实时与场景来源优先级、预测输入质量以及缺测窗口处理。

### 7.2 多级 DerivedProduct 血缘已经通过影响分析验证

CNN 是提供 Capability 的计算型 Resource，执行继续复用 Command 状态机。预测输入和输出都有稳定 ID、生成时间、有效时间、输入引用与因果 ID；模型失败复用 Command 的 `failed` 状态，不产生预测产品。

`water.flood.forecast.required` 是确定性规则已经决定需要计算后的领域事件，同时规则直接提交 Intent。它用于通知和审计，不把调度职责交给外部 Agent。

影响评估进一步证明下游计算可以引用具体预测产品，并将参数签名纳入产品身份，不再依赖 `latest`。相同输入与参数安全复用，参数变化产生并存产品；但仍需定义多个产品之间的替代关系、失效语义、超时、取消和保留策略。

### 7.3 引入一个真实控制型水工程

采样间隔控制验证了安全命令机制，但风险仍然有限。下一步需要选择一个可安全模拟的闸门、泵站或水库控制 Resource，验证：

- 参数范围和变化速率限制；
- 多个 Agent Intent 的冲突；
- 审批有效期和操作者身份；
- 设备离线、执行超时和状态回退；
- 人工接管和 `outcome_unknown` 处置。

### 7.4 建立 Agent Runtime 无关的接入面

当前已经提供统一 API：

```text
list/get Resources
query Projections
query DerivedProducts
subscribe Domain Events
submit Intents
approve/reject Commands
inspect Command history
```

Pi、OAG 和其他 Agent Runtime 应通过同一 API 接入。适配器只转换各自的工具协议，不复制领域状态与安全规则。当前 Intent、批准和拒绝 HTTP API 已进入同一状态机，但调用方身份仍是自声明字段，生产部署前必须增加认证与授权。

### 7.5 自动演进与持久化恢复已经统一

Domain 播放器现在是配置领域数据库时的自动演进生产者。播放调度只决定何时推进，实际业务步骤由 `FloodImpactDomainSystem.advance()` 完成；阈值触发、预测和影响链仍属于 Domain System。UI SSE 只投射运行状态与边界进度，不再承担领域编排。

`projection_epoch` 解决了场景重新开始时模拟时间回退与 Observation 不可变之间的冲突。临时数据库副本上的真实 HTTP 检查证明新 epoch 能取得 Projection，服务重启后也能从完整事实日志恢复同一视图。

## 8. 下一里程碑

下一里程碑定义为“完成剩余决策与行动能力迁移，并建立生产身份边界”。Runtime 无关的读取、事件游标/SSE、GIS 产品 DTO、OAG 只读工具和自动演进生产者已经建立：

```text
Projection / DerivedProduct / Domain Event
  → Runtime 无关 Query + SSE API
  → 兼容 DTO
  ├── GIS 预测图层与影响对象面板
  └── OAG 查询工具与事件上下文
```

现有 HTTP 服务可以从持久化 Domain OS 运行记录恢复查询视图；水动力和影响接口携带具体产品 ID 时直接读取产品 artifact，不复制状态到旧 Workspace。配置领域数据库后，GIS 前端恢复预测与包络评估并订阅增量事件，OAG 动态获得 Projection、DerivedProduct、Command 和 Domain Event 只读工具。后台事件 prompt 只携带已验证的具体引用；未关联的旧事件不会绑定另一个运行的最新产品。Intent、批准和拒绝通过专属事件循环宿主进入同一 DomainRuntime，避免跨线程 SQLite/asyncio 使用；自动演进也已经通过同一宿主进入 Domain System。

下一步先补齐认证和 Capability 级授权，再把路线规划改造成引用具体预测与影响产品的计算能力，并将应急指令迁移为受策略、审批和反馈确认治理的 Intent/Command。OAG 写操作只能在身份与授权边界完成后接入。详细契约见 [查询、事件与 GIS 兼容边界](04-查询事件与GIS兼容边界.md)和 [Intent、审批与 Command 接入边界](05-Intent审批与Command接入边界.md)。
