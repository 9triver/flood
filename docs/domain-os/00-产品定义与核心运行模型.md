# 面向智能体的领域操作系统：产品定义与核心运行模型

> 状态：概念验证基线
>
> 日期：2026-08-26
>
> 参考领域：水利防洪

## 1. 产品定义

面向智能体的领域操作系统，是运行在 Agent Runtime 与领域基础设施之间的长期在线软件底座。它将设备、业务系统、专业模型和数据服务组织成 Agent 可以理解但不能绕过治理直接操控的领域环境。

它负责四件核心事情：

1. 持续接入真实基础设施，把协议消息转化为有来源、有时间和有质量语义的领域事实。
2. 根据事实维护当前权威领域状态，并向 Agent 和业务应用发布稳定的领域事件。
3. 接收 Agent 的领域意图，经能力约束、策略判断和必要的人工审批后生成基础设施命令。
4. 跟踪命令从下发、受理到现实状态改变的全过程，形成可审计的闭环。

这里的“操作系统”表示它为领域智能体提供共享运行环境和受治理的 I/O 边界，而不是模拟 Linux 的进程、文件系统或系统调用，也不是将大模型包装成聊天机器人。

### 1.1 与 Agent OS 的区别

| 维度 | Agent OS / Agent Runtime | 面向智能体的领域操作系统 |
|---|---|---|
| 核心对象 | 模型、提示词、会话、记忆、任务步骤 | 资源、观测、状态、能力、意图、命令 |
| 生命周期 | 一次会话或一次任务为主 | 与领域基础设施一起长期运行 |
| 主要输入 | 用户消息、上下文、模型输出 | 遥测、告警、业务事件和 Agent Intent |
| 主要输出 | 文本、工具调用、任务结果 | 领域事件、受控命令和可确认的状态变化 |
| 正确性来源 | 推理过程与工具结果 | 权威数据、确定性策略和基础设施反馈 |
| 对设备的关系 | 通常作为一个工具调用 | 设备本身是受管理、可观测、可控制的 Resource |

Pi、OAG 或其他 Agent Runtime 都是本系统的外部客户端。它们可以订阅领域事件、查询 Projection、提交 Intent，但不进入领域内核，也不能直接获得协议级设备控制权。

### 1.2 行业无关与领域实例

内核只定义跨行业稳定的运行语义，不认识“水位”“闸门”或“洪水”。具体领域负责提供：

- Resource 类型、属性和关联；
- Observation 指标及质量规则；
- Capability、参数约束和风险等级；
- Driver 的协议映射；
- Policy 与审批规则；
- 领域事件、派生状态和专业模型能力。

水利防洪是第一个纵向实例。后续可以用同一内核承载能源、交通、工业或园区运维，而无需让这些领域共享一套臃肿的业务本体。

## 2. 核心抽象

### 2.1 Resource

`Resource` 是系统管理的现实对象或外部系统端点。它具有稳定 ID、领域类型、负责接入的 Driver，以及允许暴露的 Capability 集合。

资源不是一份静态主数据记录。它是观测、状态、能力、命令和审计记录的共同锚点。例如 `water.station/808J1510` 表示一个具体水文站，而不是 MQTT topic。

### 2.2 Observation

`Observation` 是 Driver 从外部世界接收到的不可变事实。至少包含：

- 全局可去重的观测 ID；
- Resource 与指标名称；
- 指标值和单位；
- 设备观测时间 `observed_at`；
- 系统接收时间 `received_at`；
- `good`、`suspect`、`bad` 质量标记；
- 可选序号、来源引用和协议属性。

坏数据和迟到数据仍然是事实，因此进入 Observation 日志；但它们不能无条件覆盖当前状态。

### 2.3 Projection

`Projection` 是从 Observation 派生的当前权威状态。第一版采用每个 Resource、每个 metric 的最新有效值投影：

- `bad` 观测不更新 Projection；
- 更早的观测不能倒退 Projection；
- 同一 Observation ID 重复到达时不重复产生事件；
- Projection 保留来源 Observation ID 和双时间语义。

未来的空间聚合、设备健康度、洪水态势等派生 Projection 应建立在同一事实流上，而不是让 Agent 自己在上下文中维护“当前状态”。

### 2.4 Capability

`Capability` 描述 Resource 对外公开的领域动作，例如“设置采样间隔”“调整闸门开度”。它具有稳定 ID、说明、幂等语义和风险等级。

Capability 是治理契约，不是 Python 函数名或 MQTT payload。Agent 只能针对 Resource 已公开的 Capability 提交 Intent。

### 2.5 Intent 与 Command

`Intent` 表示某个 Actor 希望达成的领域目标，包含目标 Resource、Capability、参数、理由和关联 ID。Actor 可以是 Agent、人或上层业务系统。

`Command` 是内核对 Intent 作出策略决定后建立的受控执行记录。第一版状态机为：

```text
                      ┌────────── rejected
Intent → Policy ──────┤
                      ├────────── pending_approval → dispatching
                      │                                  │
                      └────────── dispatching ───────────┤
                                                         ├── failed
                                                         ├── outcome_unknown
                                                         ├── confirmed
                                                         └── acknowledged
                                                                │
                                                  new Observation + Reconcile
                                                                │
                                                                ▼
                                                            confirmed
```

`acknowledged` 只说明基础设施接收了命令，不表示现实状态已经改变。需要状态确认的命令，只有在下发之后收到的新 Observation 与期望状态一致时才进入 `confirmed`。

如果进程在 `dispatching` 阶段中断，重启后无法仅凭本地信息判断基础设施是否已收到命令。内核将其恢复为 `outcome_unknown`，保留给后续查询、遥测协调或人工处理，不自动重发可能产生现实影响的操作。

### 2.6 Driver

`Driver` 是内核与真实基础设施之间的端口实现，职责包括：

- 建立、维持和关闭外部连接；
- 将协议消息规范化为 Observation；
- 将 Command 转换为协议命令；
- 返回基础设施受理结果和期望确认状态；
- 暴露连接与健康状态。

MQTT、HTTP、OPC UA、数据库 CDC、厂商 SDK 都只是 Driver 可以采用的技术。协议不会成为领域内核抽象。

当前 `PahoMqttTransport` 使用 Eclipse Paho 客户端实现真实 MQTT 连接，提供 TLS CA 校验、连接状态、SUBACK 等待、QoS 1 发布确认、异常断线后的自动重连和 `on_connect` 重订阅。Transport 只处理协议可靠性；topic 与 Observation/Command 的语义映射仍然属于水利 Driver。

### 2.7 Policy 与 Reconciliation

`Policy` 是确定性控制面。它根据 Actor、Resource、Capability 和上下文决定拒绝、直接执行或要求审批。当前参考策略允许低风险动作、审批受控动作，并默认拒绝关键动作。

`Reconciliation` 是现实状态控制环。它比较 Command 的期望状态与下发后产生的 Projection，确认动作是否生效。生产实现还需要超时、重试、冲突处理、补偿和人工接管机制。

### 2.8 Persistence 与 Recovery

`DomainStore` 保存三类记录：不可变 Observation、可更新 Command 和不可变 Domain Event。Resource、Capability 与 Driver 不进入数据库，它们仍由领域配置装配，避免把连接对象或协议实现错误地当成业务状态。

当前 `SqliteDomainStore` 提供单进程持久化。DomainRuntime 启动时执行：

1. 按到达顺序载入 Observation，并应用相同的质量和时间规则重建 Projection。
2. 恢复 Command，并校验历史 Driver 仍然负责目标 Resource。
3. 恢复 Domain Event 时间线。
4. 将遗留的 `dispatching` Command 转为 `outcome_unknown`。
5. 对 `acknowledged` Command 与已恢复的 Projection 再次执行 Reconciliation。

Projection 不作为独立真相持久化。它是 Observation 的可重建读模型，避免缓存状态与事实日志长期分叉。

## 3. 运行闭环

### 3.1 感知路径

```text
IoT / 业务系统
  → Driver 接收协议消息
  → 生成 Observation
  → 幂等记录与质量判断
  → 更新 Projection
  → 发布 Domain Event
  → Agent 或业务应用消费
```

Agent 看到的是经过治理的领域状态与事件，而不是未经解释的 topic、寄存器地址或厂商 JSON。

### 3.2 控制路径

```text
Agent / 人 / 上层系统
  → 提交 Intent
  → 校验 Resource 是否公开 Capability
  → Policy 决策
  → 必要时人工审批
  → 建立并下发 Command
  → Driver 映射为基础设施协议
  → 记录 acknowledged / failed
  → 用后续 Observation 做 Reconciliation
  → confirmed 或进入异常处置
```

该路径禁止 Agent 绕过内核直接发布 MQTT 命令。自然语言推理可以提出意图，但权限判定、参数边界、审批和最终状态确认必须由确定性软件承担。

## 4. 当前水利纵向实例

第一条闭环选择水文站采样间隔控制，因为它同时具备实时观测、基础设施控制、风险审批和反馈确认四种语义。

```text
Resource:   water.station/808J1510
Driver:     water.infrastructure.mqtt-hydrology
Capability: water.station.set-sampling-interval

Telemetry:  water/stations/808J1510/telemetry
Command:    water/stations/808J1510/commands
```

`water` 是默认 topic 前缀。不同环境可以配置独立前缀，例如公共测试使用 `agent-domain-os/smoke/{run_id}/water`，避免不同运行实例互相读取或覆盖消息。

遥测示例：

```json
{
  "message_id": "telemetry-42",
  "observed_at": "2026-08-26T09:01:00+08:00",
  "sequence": 42,
  "quality": "good",
  "metrics": {
    "water_level_m": {"value": 246.8, "unit": "m"},
    "sampling_interval_seconds": {"value": 10, "unit": "s"}
  }
}
```

Agent 提交将采样间隔调整为 10 秒的 Intent 后，由于该 Capability 是 `controlled`，Command 先进入 `pending_approval`。操作员批准后，Driver 发布 MQTT 命令；设备或网关受理时进入 `acknowledged`；只有新的遥测报告 `sampling_interval_seconds = 10` 后才进入 `confirmed`。

自动化测试使用 `InMemoryMqttTransport` 保持确定性；`PahoMqttTransport` 已通过 Eclipse Mosquitto 官方 `test.mosquitto.org:8883` 完成 TLS 真实闭环验证。公共 Broker 不提供隐私、隔离或服务可用性承诺，因此不能承载真实业务数据。

## 5. 代码结构与职责

| 路径 | 职责 |
|---|---|
| `domain_os/models.py` | 行业无关的值对象与命令状态机数据 |
| `domain_os/contracts.py` | InfrastructureDriver 与 DomainPolicy 端口 |
| `domain_os/runtime.py` | 注册、感知、事件、意图、命令和协调循环 |
| `domain_os/policy.py` | 最小风险策略实现 |
| `domain_os/persistence.py` | DomainStore 序列化和 SQLite 持久化 |
| `domain_os/transports.py` | MQTT 契约、内存实现和 Eclipse Paho 实现 |
| `domains/flood/domain_system.py` | 水利资源装配、MQTT 映射与领域便捷 API |
| `scripts/check_domain_mqtt.py` | 真实 MQTT Broker 纵向闭环检查 |
| `tests/test_domain_os_runtime.py` | 从遥测到控制确认的纵向测试 |

旧有 `server/` 和 `domains/flood/runtime/` 暂时作为水利能力资产与演示应用保留。它们尚未全部迁入新内核，不能被误认为新架构已经完成。

## 6. 设计原则

1. **现实状态优先**：Agent 的回答、记忆或工具返回值都不能替代基础设施事实。
2. **意图与协议隔离**：Agent 表达领域意图，Driver 独占协议细节。
3. **默认受治理**：所有控制行为经过 Capability 和 Policy，不提供旁路。
4. **确认而非假设**：命令被接受不等于执行成功，必须依赖反馈协调。
5. **事实不可抹除**：迟到、重复和坏数据有明确处理语义并可追溯。
6. **内核保持最小**：只提炼被真实领域闭环证明必要的扩展点。
7. **Agent Runtime 可替换**：Pi、OAG 或其他运行时通过相同领域 API 接入。

## 7. 下一阶段

下一阶段不先扩展通用插件系统，而是继续完成水利领域骨架：

1. 将现有水文演进输入接为 Observation，将洪水预测注册为由领域事件触发的专业能力。
2. 增加至少一个具有安全边界的水工程控制 Resource，验证超时、冲突和人工接管。
3. 在私有 Broker 上补充设备身份、topic ACL、离线消息和消息积压策略。
4. 提供独立于具体 Agent Runtime 的查询、事件订阅和 Intent API，再分别验证 OAG 与 Pi 客户端。
5. 在真实负载下评估 SQLite Store，再决定事件总线、数据库和高可用部署方案。

只有当多个真实 Driver 或领域模块出现相同装配需求时，才进一步抽象插件发现、依赖解析和生命周期机制。
