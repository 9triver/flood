# 领域操作系统

领域操作系统的本质，不是“给 Agent 准备很多工具”，而是为 Agent 建立一个可信、持续存在、可操作的领域世界。

今天的大多数 Agent 系统解决的是“如何思考”：对话、记忆、规划、工具选择和模型调用。但进入真实业务后，更困难的问题是：

- 当前世界到底是什么状态？
- 数据来自哪里，是否过期，是否互相矛盾？
- Agent 是否有权执行某个动作？
- 多个 Agent 同时操作时如何处理冲突？
- 命令发出后，现实是否真的发生了变化？
- 系统重启后，先前的判断和操作能否恢复、解释和追责？

领域操作系统主要解决这些问题。

## 把现实世界变成一台可操作的领域机器

原始业务世界通常由设备、数据库、模型服务、人工流程和第三方系统组成。它们的数据格式、时间语义、可靠性和权限模型各不相同。

领域操作系统通过驱动和适配器把这些对象挂载成统一世界。上层看到的不再是 MQTT 消息、数据库表或 HTTP 接口，而是稳定的领域状态，例如：

```text
某个站点的当前水位
某条道路的通行状态
某次预测的结果和有效时间
某个控制动作的审批与执行状态
```

这类似传统操作系统把磁盘、网卡和进程统一为文件、套接字和系统调用。底层设施可以变化，上层面对的领域语义和操作纪律应当保持稳定。

## 最重要的产物是世界秩序

领域操作系统最重要的产物不是一组 API，而是业务世界中的秩序。一个真正的领域操作系统至少需要建立五种秩序。

### 状态秩序

系统必须明确什么是原始事实、当前状态、历史观测和派生结论，不能让多个应用分别维护一份彼此矛盾的“最新状态”。

### 时间秩序

系统需要区分观测时间、接收时间、计算时间、预测有效时间和操作时间。真实业务中的很多错误并非数值错误，而是把具有不同时间语义的数据拼在了一起。

### 权限秩序

Agent 不能因为“拥有某个工具”就天然拥有业务权限。权限必须约束到主体、对象、动作、条件和有效期，并在真正产生副作用的边界上执行检查。

### 因果秩序

“发出命令”和“现实改变”是两件事。动作应当经历意图、审批、派发、反馈和确认，最终状态必须由新的现实证据决定。

### 责任秩序

每个事实、判断、模型产物、人工决定和控制动作都需要可追溯。系统必须能够回答“为什么会得到这个结论”“依据是什么”以及“是谁让它发生的”。

## 从信号到现实反馈的完整闭环

一个完整的领域闭环应当是：

```text
信号 -> 可信事实 -> 状态变化 -> 规则或 Agent 判断
     -> 操作意图 -> 权限与人工审批 -> 命令派发
     -> 现实反馈 -> 一致性裁决 -> 新的可信状态
```

其中最关键的是最后的反馈裁决。没有它，系统只是一个工具调用平台；有了它，系统才开始具备操作系统意义上的一致性。

一次调用成功，只能说明命令被某个接口接受，不能证明现实已经改变。领域操作系统必须继续等待晚于命令派发的反馈证据，并据此判断操作已完成、已失败，或者结果仍然未知。对于具有现实副作用的动作，“结果未知”本身就是一种必须被认真处理的状态，而不是可以被静默重试的普通异常。

## Agent、确定性进程与人的分工

领域操作系统中的智能不应全部集中在大模型里。基本分工是：

- 确定性进程负责条件反射，例如阈值检测、完整性检查、必须执行的规则和周期任务。
- Agent 负责理解复杂情境、组合专业能力、处理不完整信息并形成解释或建议。
- 人保留高风险决策、授权和责任承担。

不能让大模型承担系统的基本生命维持功能，也不能让固定规则处理所有开放情境。领域操作系统负责让三者在同一个世界状态和操作纪律下协作。

确定性进程保障“即使 Agent 不在线，必须发生的事情仍然会发生”；Agent 保障“系统能够理解规则尚未覆盖的复杂情境”；人工确认则保障“高风险权力仍然对应明确的责任主体”。

## 与相近概念的区别

### 与 Agent 框架的区别

Agent 框架管理模型如何思考，包括会话、上下文、规划和工具选择；领域操作系统管理 Agent 所处的世界，包括状态、权限、事务、反馈和恢复。

Agent Runtime 可以更换，领域世界不应随之消失。

### 与数字孪生的区别

数字孪生侧重描述、映射和模拟现实；领域操作系统还必须处理权限、操作、事务、反馈和故障恢复。它不仅回答“世界是什么样”，还要治理“谁能够如何改变世界，以及如何证明改变已经发生”。

### 与工作流引擎的区别

工作流引擎描述预先设计的步骤；领域操作系统提供多个工作流、进程和 Agent 可以共同运行的底层状态与控制机制。工作流可以建立在领域操作系统之上，但不应拥有另一份相互竞争的世界状态。

### 与集成平台的区别

集成平台负责传递数据和调用接口；领域操作系统还要决定哪些数据构成事实、谁能改变什么，以及一次操作最终是否成功。

### 与领域本体的区别

领域本体解决“这个世界中的对象和概念叫什么、具有什么属性和关系”；领域操作系统进一步解决“这些对象如何变化、谁能操作、变化如何被证明”。

本体提供语义，操作系统提供运行纪律。二者结合后，Agent 才既能理解领域，又能在领域中安全行动。

## 多个 Agent 共享同一个世界

领域操作系统允许不同 Agent Runtime 共享同一个可信世界，而不是让每个 Agent 都通过提示词和临时工具结果构造自己的现实。

Agent 可以被替换、重启、升级甚至暂时离线，但领域状态、未决事务、审计记录和现实约束仍然存在。新的 Agent 接手后，应当能够从系统状态继续工作，而不是依赖上一段对话记忆猜测发生过什么。

这也意味着多 Agent 协作不应主要依靠彼此发送自然语言消息。它们最可靠的协作媒介应当是共同的领域世界：一个 Agent 提交可审计的判断或产物，另一个 Agent 观察到新的世界状态后继续工作。

## 领域无关内核与领域知识的边界

领域操作系统需要一个足够稳定的通用内核，但不能追求脱离业务语义的虚假通用性。

内核适合负责：

- 唯一可信状态与历史事实；
- 设备接入和统一操作边界；
- 能力、权限和人工审批；
- 事务、一致性裁决和失败恢复；
- 进程监督、调度和审计。

领域层适合负责：

- 对象、指标和业务动作的语义；
- 原始数据如何归一化；
- 哪些条件需要触发业务过程；
- 专业模型如何计算；
- 什么现实证据能够确认某个动作；
- 哪些风险必须由人承担和批准。

内核应当薄而严格，领域驱动和领域进程可以厚而具体。换领域时需要重写领域知识，但不应重写状态、权限、事务和审计的基本纪律。

## 判断它是否真正成立

“操作系统”不能只停留在命名类比。如果只是把接口叫作 syscall、把数据库叫作 namespace，它仍然只是普通业务平台。这个概念是否成立，要看它是否真正提供了以下强约束：

- 所有重要变更是否经过唯一入口；
- 是否存在唯一可信状态以及明确的代次和时间语义；
- 是否能处理并发、过期读取和操作冲突；
- 命令结果是否由新的现实证据确认；
- 未知结果是否会阻止危险重试；
- 重启后能否恢复世界状态和未决责任；
- Agent 是否只能在被授予的边界内行动；
- 更换 Agent Runtime 后，业务闭环是否仍然成立；
- 没有 Agent 在线时，确定性的必要业务过程是否仍能运行。

如果这些条件不成立，系统更可能是一个领域工具箱、集成平台或工作流应用，而不是领域操作系统。

## 总体判断

领域操作系统是一层面向智能体的业务现实基础设施。

它的长期价值不在于让 Agent 调用工具更方便，而在于让具有概率性、可替换和可能失败的智能体进入真实业务之后，现实世界仍然保持一致、可控和可追责。

它真正保护的不是某个 Agent，而是业务世界本身的安全性、因果性和责任边界。
