# Domain OS 洪水预测纵向闭环

> 状态：第一版已实现
>
> 日期：2026-08-26

## 1. 目标与边界

本轮不是把旧水利应用整体搬入新内核，而是先证明一条最小但真实的业务路径：当前水文事实进入 Domain OS，确定性规则触发受治理的 CNN 计算，结果成为可追溯的预测产品。

这条路径刻意保持三类信息的边界：

| 信息 | Domain OS 表达 | 示例 |
|---|---|---|
| 已经发生或被报告的当前事实 | `Observation`，并更新 `Projection` | 当前边界流量、降雨、水库水位 |
| 场景提供的未来边界条件 | 输入 `DerivedProduct` | 当前至未来 24 小时的 25 个时点 |
| 专业模型计算结果 | 输出 `DerivedProduct` | 最大水深、淹没单元、时间序列文件 |

未来 CSV 行不能因为读取方便而提前成为 Observation，CNN 结果也不能直接覆盖现实 Projection。

## 2. 运行路径

```text
边界流量 CSV / 后续预测数据源
  → BoundaryFlowEvolutionDriver
  → 当前时刻 10 条 Observation
  → Resource Projection
  → sequence 更新事件
  → 25 点 forecast-input DerivedProduct
  → 窗口峰值 > 230 m3/s 的确定性规则
  → water.flood.forecast.required
  → Intent → Policy → Command
  → FloodForecastModelDriver → CNN V2
  → water.flood.forecast DerivedProduct
  → Command confirmed
  → water.flood.forecast.generated
```

每个演进时刻共报告十条 Observation：四条边界流量、一条降雨、一条流域边界总流量、三条水库指标和最后一条 sequence 标记。sequence 最后到达，保证规则执行时当前快照已经完整。

## 3. 领域映射

### 3.1 Resource

| Resource | 角色 |
|---|---|
| `water.boundary/{interval1,interval2,tonggu,upstream}` | 四个水动力边界 |
| `water.watershed/shanhu` | 降雨、总流量和预测产品的领域主体 |
| `water.reservoir/longtan` | 入流、下泄和水位的现实对象 |
| `water.evolution-source/boundary-flow` | 演进序列来源 |
| `water.model/flood-cnn-v2` | 提供预测 Capability 的计算型 Resource |

### 3.2 输入产品

`water.flood.forecast-input/{run_id}/{sequence}` 是不可变输入快照，包含：

- 25 个整点、跨度 24 小时的四边界流量序列；
- 同一窗口的降雨序列和当前水库水位；
- 阈值、窗口峰值、首次超限时间和规则版本；
- 生成时间、有效时间、演进 episode 以及触发 sequence Observation 引用。

当前实现使用场景 CSV 提供未来窗口。换成真实系统后，生产者可以替换为水文预报服务 Driver，但产品和模型契约不需要随协议变化。

### 3.3 计算命令与输出产品

规则以 `water.rule.forecast-trigger` Actor 提交 `water.flood.run-forecast` Intent。CNN 被装配为低风险计算 Capability，因此仍经过 Resource、Capability、Policy、Command 和 Driver 边界，但不需要人工审批。

成功时，Driver 返回 `water.flood.forecast/{run_id}/{sequence}`，其中：

- `input_refs` 指向唯一的输入产品；
- `valid_from`、`valid_to` 继承预测窗口；
- `producer_id` 指向 CNN Resource；
- `data` 保存模型、淹没单元、水深和时间步摘要；
- `artifacts` 保存 `max_depth.csv`、`depth_series.npy` 和 `time_steps.json` 引用；
- `causation_id` 指向执行该计算的 Command。

计算没有等待现实遥测确认的状态，因此产物成功记录后 Command 直接 `confirmed`。如果模型抛出异常或返回错误，Command 为 `failed`，不生成伪造的预测产品。

Capability 声明为幂等。同一输入产品再次提交时，Driver 返回已经记录的输出产品，不重复运行 CNN，也不覆盖已经归档的文件产物。

## 4. 事件与可恢复性

关键事件按以下顺序产生：

1. `domain.observation.recorded` 与 `domain.projection.updated`。
2. `domain.product.recorded`，记录预测输入产品。
3. `water.flood.forecast.required`。
4. `domain.command.dispatching`。
5. `domain.product.recorded`，记录模型输出产品。
6. `domain.command.confirmed`。
7. `water.flood.forecast.generated`。

失败路径以 `domain.command.failed` 和 `water.flood.forecast.failed` 结束。SQLite Store 持久化 Observation、DerivedProduct、Command 和 Domain Event；重启后 Projection 从 Observation 重建，两个产品及事件时间线直接恢复。

## 6. 演进播放接入

配置 `server/app.py --domain-database ...` 后，既有 `/api/autonomy/*` 播放控制由 `DomainPlaybackController` 接管。控制器在 `DomainRuntimeHost` 所属事件循环上调度 `FloodImpactDomainSystem.advance()`，自身只负责开始、暂停、继续、停止、单步、速率和自动暂停，不判断洪水阈值，也不调用 OAG 决定是否运行预测。

每次开始新一轮或切换 CSV 数据源都会建立新的 `evolution_run_id`，并把它作为该场景 Observation 的 `projection_epoch`。同一个 DomainRuntime 和 SQLite 时间线继续保留，新的 Observation、预测输入、预测产品、影响产品、Command 和 Event 使用新 run ID，不覆盖上一轮不可变记录；即使新场景从更早模拟时间开始，相关 Resource 的 Projection 也会从新 epoch 重建。已经退役 run 的迟到 Observation 不能切回旧 Projection。上传源仍复用原 `/api/autonomy/sources` 契约，但 Domain 模式不创建或写入旧 Workspace。

两个 SSE 通道的职责明确分开：

- `/api/autonomy/stream` 只发送 `runtime_status` 和 `boundary_flow_data`，供现有播放控件与遥测面板显示进度；
- `/api/domain/events/stream` 发送权威 Domain Event，预测与影响产品仍由具体产品 ID 驱动 GIS 更新；
- Domain 模式不会产生 `FloodForecastRequired`、`InundationGenerated` 等旧自治事件，也不会把新事件交给 `EventAgentProcessor` 再运行一遍模型。

未配置 `--domain-database` 时仍使用原 `EventRuntime`，保证迁移期间旧启动方式可运行。OAG 写操作、路线规划和应急指令尚未完成同等迁移，不能据此宣称原应用已经整体迁移。
